# Experimental Niri width memory

Enable automatic startup with `./install.sh --dry-run --feature width-startup` followed by `./install.sh --feature width-startup`. Niri starts the helper at the next session using `spawn-at-startup`. The checkout must remain at the same path. Run `python3 features/niri_width.py` inside a Niri session for a manual test; Ctrl+C stops that instance. A per-user runtime lock prevents duplicate instances. The printed rollback command restores the Niri configuration to its state before enabling startup. It keeps one width per Niri app ID in `$XDG_STATE_HOME/vylmods-niri-dms/widths.json` (default `~/.local/state/vylmods-niri-dms/widths.json`) and restores it on newly opened tiled windows. Existing windows are not resized when the tool starts. Delete the state file to forget widths. It never changes window height or Niri configuration.

Niri 26.04 does not identify the cause of a width change or expose fullscreen state in its window IPC. The prototype skips windows that cover at least 90% of both display dimensions as a conservative fullscreen heuristic; this can also skip wide regular windows and is not a guarantee. It can still save layout-driven width changes and can affect other windows in the same column. Output sizes are captured at startup; restart the prototype after changing displays or scaling. It does not cover floating windows, apps without an app ID, multiple distinct widths for one app, or changes while it is stopped. There may be a visible resize on opening. The basic width behavior has been tested by the user; automatic startup must still be checked after restarting the Niri session.
